Running a Bot Team on Less: Conserving Grok Bot Usage

Most of Jacob's Grok Bot usage is chat work, not routines. Better cron hygiene helps a little. Changing how the Kapsoul bots get briefed, how long their threads run, and how much they talk to each other saves far more.

Assigned by Jacob Peterson · Research. Checked Nov 2, 2026. Points tagged [Jacob's data] come from Jacob's own usage report for Oct 3 – Nov 2, 2026, given as shares of all Grok Bot usage. Points tagged [Best practice] are general guidance. This report gives no projected savings or run counts beyond the report's own numbers. Nothing was changed; this is a report only.

SummaryBottom line

1The routines aren't the problem. The chat is.

[Jacob's data] About 85–90% of usage is interactive or delegated chat work, not routines. Kapsoul's three bots (Sentinel 17%, Atlas 13%, Forge 10%) make up about 40% of the total, nearly all of it outside routines. Even the busiest routine, ShipSonar's stuck-order watch (about 336 runs a week), is only about 1%.

Top 3: (1) Put the Kapsoul bots on tight briefs and fresh threads. (2) Cut bot-to-bot chatter: status pings, wrap-ups and relays. (3) Move deterministic checks such as stuck orders, sensitive paths and deadline reminders to plain scripts, webhooks or GitHub Actions. The routine fixes (lower cadence, waking hours only, triggers) are easy, but they're the smaller wins.

Interpretation of Jacob's usage report.

1Ranked recommendations

1.1Tight briefs and fresh threads for Sentinel, Atlas and Forge [Jacob's data + Best practice]

What changes: give each Kapsoul task one goal, the files or areas it covers, a "done when" line and an output format, such as "Return a pass/fail list, max 10 lines." Start a new thread for each task instead of continuing one long thread for days. Paste a 5-line handoff summary in place of the old history.

Why: Cursor counts context as input tokens. On Grok 4.7, input past 256k tokens is billed at 2× standard rates. A long thread re-sends its history every turn, so later turns cost more than earlier ones. Open-ended QA ("test everything") leads to wide exploration. Sentinel alone is 17%.

Tradeoff: it takes a minute of setup per task, and a new thread loses whatever history you didn't carry over. Keep a short "Kapsoul state" note the bots can read.

Cursor: Models & Pricing (long-context rates) · Cursor: larger context increases tokens

1.2Cut chat between bots [Jacob's data + Best practice]

What changes: no status pings, "acknowledged" replies or daily wrap-ups between bots. Bots message each other only to hand off work or flag a blocker. Results go into one shared file or page that people read, instead of being sent around. Don't use a PM bot that relays between bots and repeats their output.

Why: every message to a bot wakes it, which starts a full turn with context loaded. 41% of "other bots" usage happens outside routines, which is where relay chatter shows up. Grok Bot's own usage guidance says the same: messaging another bot wakes it and uses usage.

Tradeoff: less real-time awareness, so you read the shared status file instead of getting updates pushed to you.

Jacob's usage report; this bot's usage-review guidance.

1.3Move deterministic checks out of Grok Bot [Jacob's data + Best practice]

What changes: replace checks that need no judgment with a script on cron, a GitHub Actions schedule workflow, or a Supabase/Vercel cron. That covers the stuck-order watch (a query plus a threshold), the 12-hour sensitive-path check (a diff or grep), and the Kapsoul safety deadline reminders (date math). The script calls a bot only when something is actually wrong. This was already done for PromptPatrol face watch.

Why: a script costs no Grok Bot usage on the runs where everything is fine. The bot is only needed to interpret a problem.

Tradeoff: someone has to maintain a small script and its secrets, and an unexpected edge case won't get judged by a bot.

GitHub Docs: schedule event · Vercel Cron Jobs · Supabase Cron

1.4Switch from schedules to triggers [Jacob's data + Best practice]

What changes: instead of polling every 30 minutes for stuck orders, react to events: a Stripe webhook (such as a failed or delayed payment), a GitHub push for sensitive paths, or an email or Slack message.

Why: a trigger only runs when something happens. The stuck-order watch runs about 336 times a week, and most of those runs presumably find nothing.

Tradeoff: short setup, the app has to be connected, and a missing event (one that never fires) needs a backup, such as one daily sweep.

Stripe: Webhooks · GitHub: Webhooks

1.5Lower cadence, waking hours only, and merge duplicates [Jacob's data]

What changes: run Kapsoul deadline reminders (~56/wk) a few times on weekdays only. Combine Keeper's X lead scout, Higgsfield Discord reply check and Discord copycat watch into one "social sweep" twice a day in waking hours. Consider merging the IG staggered follows (~42/wk) with the IG daily run. Delete, rather than keep, any of Hull's paused status routines that are no longer needed.

Why: nobody acts on results at 3 AM, and one merged run loads context once instead of three times.

Tradeoff: results are less fresh, and overnight issues wait until morning. These routines are each about 1%, so this is cleanup, not the main fix.

1.6Low effort for lookups, high effort only for hard problems [Best practice]

What changes: ask for a quick answer on simple facts, status reads and formatting. Save deep reasoning and multi-source research for architecture, debugging and reports.

Why: Cursor says model choice affects how fast included usage runs down, and its price table shows "Fast" variants at about 2× standard rates.

Tradeoff: a quick answer can miss a subtlety, so escalate when one does.

1.7Cache research and reuse it [Best practice]

What changes: save research results (pricing tables, API limits, competitor notes) to files in the repo or store with a "checked on" date. Bots read the file before searching the web again. TheGapBrief reports already work as a cache.

Why: re-researching the same facts costs search and page reads every time. Reading one short file costs much less.

Tradeoff: cached facts go stale. Set a re-check date, such as 30 days.

General practice.

1.8Use the browser and desktop only as a last resort [Best practice]

What changes: prefer a connector or API (Zernio, GitHub, Supabase, Stripe) over driving a browser. When browser work is needed, give the exact URL and the exact thing to read.

Why: screenshot-and-click loops take many steps and carry a lot of context per step. An API call is one step.

Tradeoff: some sites have no API.

General practice.

1.9Batch asks, and merge overlapping bots [Jacob's data + Best practice]

What changes: send one message with five asks instead of five messages. Consider merging the Kapsoul bots into fewer bots, or have Forge and Atlas share a single "Kapsoul state" file so each doesn't rebuild the same picture.

Why: each new turn or new bot loads its context again.

Tradeoff: a merged bot has a bigger, more general role and can lose focus. Merge only where the work overlaps.
